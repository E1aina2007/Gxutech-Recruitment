### 平时如何使用 AI？

主要用在三类场景：一是读别人的代码和陌生 API 时，让 AI 先给一张「地图」，再回到官方文档核对细节；二是解释报错，尤其是编译器和链接器那种很长的输出，让它帮我抓关键行；三是生成样板代码和重复性脚本。我的原则是：**AI 给出的任何结论，都要配一个我自己的验证动作**——跑一次最小复现、翻官方文档，或者用 `git cat-file` 这类权威工具对比输出。验证不了的说法我不会直接用。

### 如果 AI 给出的答案明显不对，你会怎么处理？

我不会急着换一个问题，而是先把「错在哪」定位清楚，一般按这个顺序：

1. **做最小复现**：把无关代码全删掉，只留下能稳定复现问题的部分，确认问题边界；
2. **和一手资料对照**：拿 AI 的结论去比对官方文档、源码，或用 `git cat-file`、`ls-remote` 这类权威工具的实际输出；
3. **带着反例重新提问**：如果发现是我给的前提有偏差，就明确告诉它「这个结论在 X 情况下不成立」，修正前提再问一次；
4. **承认它不可靠并换路径**：如果仍然不对，说明这个问题超出了它的可靠范围，转向官方文档、issue tracker 和源码去查，或者换一个思路，而不是在错误结论上继续叠加。

## AI 辅助记录

### 1. 我遇到的问题

做本次 PR 提交时，本机环境有两处限制：**没有安装 `gh` CLI**；网络环境下 **SSH 的 22 端口被直接断开**（`ssh -T git@github.com` 连接被拒）。也就是说，我必须在「不使用 `gh`、也不把凭据明文写进任何命令或文件」的前提下，自己完成「fork 仓库 → 推送分支 → 创建 PR」的全过程。

### 2. 我是怎么向 AI 提问的

我把环境约束一次性说清楚，再要一条最小可行路径，提示词大意是：

> Windows + Git Bash，没有 gh CLI，22 端口 SSH 不通，HTTPS 可以正常访问 GitHub。需要完成 fork → push → 创建 PR。要求：不安装新工具、不把 token 写进任何会被提交的文件、每一步都给出可验证的命令，并说明这一步怎么验证成功。

### 3. AI 的回答有没有直接解决？

**部分有效，但没有直接可用。** 主干思路是对的（用 GitHub REST API 代替 `gh`），但它默认了我「有 `gh`、SSH 可用」，第一步 `gh repo fork` 在我这儿根本不成立；它还建议把 token 直接拼进远程 URL，这会把凭据留存在 `.git/config` 里，我没有采纳。

我按自己的判断调整成了三步，每步都带验证动作：

1. 用 `git ls-remote` 确认 HTTPS 连通性、并拿到上游最新的 `refs/heads/main`；
2. 用 `git credential fill` 确认凭据能被 git 自动取用（全程不打印明文），从而确定推送不需要我手工传 token；
3. 用 `curl` 调 `POST /repos/{owner}/{repo}/forks` 创建 fork，**看 HTTP 状态码和返回 JSON 里的 `full_name` 字段**来确认成功，而不是凭感觉认为成功。

### 4. 如果没有，我后来怎么继续处理？

创建 PR 时确实先失败了一次：fork 刚建好就去调创建 PR 的接口，返回了 404。我没有直接重试，而是先**读响应体里的 `message` 字段**（光看状态码只会以为是自己写错了参数），确认是 fork 还没初始化完成，于是改用 `GET /repos/{owner}/{repo}` 轮询，直到能读到默认分支 `main`，再发起 PR。

这件事让我更确定一点：AI 给的是「一般情况下应该怎么做」，而具体环境里的约束——有没有这个工具、端口通不通、凭据存在哪——只能自己一步步验证；**报错本身往往就是最准确的线索**，先读它，再改动作。
