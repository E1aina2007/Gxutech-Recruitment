## AI 辅助记录

### 1. 我遇到的问题

报名任务要求在 GitHub 上完成分支、提交和 PR。但在准备推送代码时，我发现这台电脑上**所有基于 Windows 自带安全通道（Schannel）的 HTTPS 工具都连不上 GitHub**：`git clone`、`git push`、`curl` 全部报同一个错——

```
schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e)
```

一开始我以为是网络问题或者 GitHub 被墙，换了几个站点测试还是失败，自己判断不出到底是网络、证书还是别的原因，于是把问题交给 AI Agent 来一起排查。

### 2. 我是怎么向 AI 提问的

我没有直接问「git 用不了怎么办」，而是把**现场证据**交给它，让它先做判断：

1. 附上完整报错原文（`fatal: unable to access ... schannel: SEC_E_NO_CREDENTIALS`），并说明这台机器上 `git`、`curl`、PowerShell 的 `Invoke-WebRequest` **都**报同一个错。
2. 补充了一个我自己观察到的关键现象：`curl` 连 `https://www.baidu.com`、`https://nodejs.org` 这种跟 GitHub 完全无关的站点也失败。
3. 明确要求它先区分「网络问题」还是「本机 TLS 问题」，并给出可以逐条执行的验证方法，而不是直接给结论。

### 3. AI 的回答有没有直接解决？

**没有直接解决，但它给出的排查方向是对的，并且帮我把问题定性了。**

它先怀疑是 hosts 文件或代理问题，让我检查 `C:\Windows\System32\drivers\etc\hosts`。查下来确实发现，我用来加速的工具（Steam++）在 hosts 里把 `github.com`、`api.github.com` 等一批域名指向了 `127.0.0.1`，而本机 443 端口上确实有它的服务在监听。

但按这个结论去修并没有修好：换用不同域名、不同工具，TLS 握手依旧在很早期就失败。这说明 AI 的第一版结论**只对了一半**——hosts 是现象之一，不是根因。

### 4. 如果没有，我后来怎么继续处理？

我沿着它的思路继续做对照实验，自己补上了关键一步验证：**用 Node.js 去访问同一个网址**。

结果非常关键：Node 访问 `codeload.github.com` 成功返回 200，而 `git`、`curl` 报错。这两者的差别在于——**Node 自带一套独立 TLS 实现（OpenSSL）和自己的根证书，完全不经过 Windows 的 Schannel**。

这一步把范围锁死了：不是网络不通，也不是 GitHub 的问题，而是**这台机器的 Windows Schannel 本身无法建立 TLS 连接**，凡是依赖它的程序（git、curl、.NET）一律失败。顺着这个结论，我找到了可行的办法：

- 让 Node 信任本机证书库里的根证书：加上 `--use-system-ca` 参数后，通过加速工具的中间人证书成功访问了 `api.github.com` 和 `github.com`。
- 于是我不再依赖 `git` 命令，而是用 Node 调用 GitHub 的 REST API 来完成读取仓库、创建分支和提交推送。

这条路走通了：我成功读到了上游仓库的完整目录结构、模板文件和 CI 校验规则，也确认了 `api.github.com`、`github.com`、`raw.githubusercontent.com` 都能正常访问。**能不能真正提交，最终要以这次 PR 是否通过 CI 校验来检验**——这也是我判断一个方案是否真的有效的标准。

我的收获是：AI 帮我把问题从「git 报错」缩小到了「TLS 层」，但真正的定位是靠**对照实验**（拿一个能用的工具和一个不能用的工具做比较）完成的。这也印证了我平时用 AI 的习惯——它的答案是线索，最终必须靠自己动手验证。
